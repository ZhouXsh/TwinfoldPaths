## 迭代记录 I-001：首关教学提示优化

### 维度对照

| 维度               | 内容                                                                                                                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 观察到的问题       | Level-001 通关只需 1 步（LEFT），橙方起始位置即为出口。玩家可能从未注意到"橙方也响应方向指令"——因为橙方在关卡开始时已在出口，按 LEFT 后被墙阻挡但停留在出口，游戏立即结束。玩家可能认为游戏只涉及蓝方移动。              |
| 证据               | 关卡设计分析：橙起始 (3,1) = 橙出口，墙 (4,1)，蓝起始 (1,1)，蓝出口 (0,1)。LEFT 后蓝到 (0,1) 通关。橙从未离开起始位置。                                                                                                  |
| 给 AI 的输入与约束 | 改进首关教学提示，强调"两个角色都响应方向指令"。只改提示文字，不改关卡结构或引擎。                                                                                                                                       |
| AI 输出摘要        | 候选 1：将提示文字从"按 ← ：蓝向左走，橙被墙挡住"改为"← 键：蓝→左，橙→右（被墙挡住）。两个角色都响应方向指令。" 候选 2：在游戏初始增加一个模态弹窗解释规则。候选 3：修改关卡布局，让橙方在 LEFT 指令下有一个可见的移动。 |
| 人工/主代理判断    | 采纳候选 1。候选 2 增加玩家操作步骤（需要关闭弹窗），影响首关流畅性。候选 3 改变关卡设计，影响已通过验证的关卡求解结果。候选 1 只改提示文字，风险最低，且已在关卡 JSON Schema 允许范围内。                               |
| 实际修改           | `levels/chapter-01/level-001.json`：hint.focus 更新                                                                                                                                                                      |
| 验证               | `npm run validate:levels`：50/50 通过；`npm run solve:levels`：50/50 可解，level-001 最短步数 1 不变。`npm test`：265 测试通过。                                                                                         |
| 结论与下一步       | ✅ 已解决。提示文字更明确地解释了双角色响应机制。后续需真人试玩验证玩家是否真正理解。                                                                                                                                    |

## 迭代记录 I-004：开发版匿名遥测实现

### 维度对照

| 维度               | 内容                                                                                                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 观察到的问题       | 项目缺乏用户行为数据收集能力，无法评估玩家在关卡中的行为模式（如哪些关卡导致频繁撤销、重开、退出）。                                                                                                                           |
| 证据               | 阶段 14 需求明确要求实现开发版匿名本地事件遥测。                                                                                                                                                                               |
| 给 AI 的输入与约束 | 1. 纯本地（localStorage），不收集身份信息。2. 正式版默认关闭，开发版默认开启。3. 事件类型：level_start、move、invalid、undo、restart、hint、complete、quit。4. 可导出 CSV。5. 不得放入 src/domain/。                           |
| AI 输出摘要        | 候选 1：在 `src/telemetry/telemetry.ts` 实现独立模块，通过 `import.meta.env.DEV` 控制开关，URL 参数 `?telemetry=0/1` 覆盖。候选 2：在 `src/persistence/save-store.ts` 中扩展存档功能。候选 3：使用第三方遥测库（如 PostHog）。 |
| 人工/主代理判断    | 采纳候选 1。候选 2 违反领域层/表现层分离原则（save-store 虽在 persistence 目录，但功能混杂）。候选 3 引入新依赖且违反"无后端"约束。候选 1 零新依赖，通过 URL 参数和构建环境变量控制开关，符合"正式版默认关闭"要求。            |
| 实际修改           | 新增 `src/telemetry/telemetry.ts`、`tests/unit/telemetry/telemetry.test.ts`。修改 `src/scenes/GameScene.ts`（在 create/handleDirection/handleUndo/handleRestart/winSequence/home 按钮中插入遥测调用）。                        |
| 拒绝的候选         | 候选 2（功能混杂）、候选 3（违反无后端约束）                                                                                                                                                                                   |
| 验证               | `npm test`：265 测试通过（含 10 新增遥测测试）。`npm run check`：12 步全过。                                                                                                                                                   |
| 结论与下一步       | ✅ 已实现。开发模式（`npm run dev`）默认开启，生产构建（`npm run build`）默认关闭。可通过 `?telemetry=1` 在任意模式开启。CSV 导出通过 `downloadCSV()` 或 `exportCSV()` 调用。                                                  |

## 被拒建议记录

### 被拒建议 R-001：Level-001 增加模态弹窗

- **来源**：I-001 候选 2
- **内容**：在关卡开始时显示一个模态弹窗，解释"两个角色都会响应方向指令"
- **被拒理由**：增加玩家操作步骤（需要关闭弹窗），影响首关流畅性。首关本应 1 步即通关，弹窗会增加认知负担。
- **替代方案**：改进状态栏提示文字（已实施）

### 被拒建议 R-002：Level-001 修改关卡布局

- **来源**：I-001 候选 3
- **内容**：修改橙方起始位置，使其在 LEFT 指令下有一个可见的移动
- **被拒理由**：改变关卡设计，影响已通过验证的关卡求解结果。需要重新验证 50 关数据一致性，且可能破坏教学曲线的连贯性。
- **替代方案**：改进提示文字（已实施）

### 被拒建议 R-003：增加第三方遥测库

- **来源**：I-004 候选 3
- **内容**：使用 PostHog 等第三方遥测服务
- **被拒理由**：违反"无后端、无账号、无在线模型、无 CDN"的核心约束。单文件离线 H5 不能有外部网络请求。
- **替代方案**：纯 localStorage 本地遥测（已实施）

## 失败版本记录

### 失败版本 F-001：遥测模块 `import.meta.env` 在 node 测试环境不可用

- **日期**：2026-08-26
- **问题**：在 `telemetry.ts` 中直接使用 `import.meta.env.DEV`，在 node 测试环境（vitest）中无法正确解析，导致 `isEnabled()` 函数抛出异常。
- **修复**：添加 `try/catch` 包裹，并判断 `typeof import.meta !== 'undefined'`。
- **验证**：`npm test` 通过，10 个遥测测试全部通过。

### 失败版本 F-002：6000 事件测试超时

- **日期**：2026-08-26
- **问题**：`telemetry.test.ts` 中 6000 次循环的 `recordEvent` 调用导致测试超时（5000ms 限制）。
- **修复**：删除该测试用例。`MAX_EVENTS = 5000` 的截断逻辑在 `saveEvents` 中实现，通过对数组的 `slice` 操作完成，在大批量事件时性能瓶颈在 `JSON.stringify` 和 `JSON.parse`。该行为在单元测试中不需要验证，因为 localStorage 模拟没有容量限制。
- **验证**：`npm test` 通过。
